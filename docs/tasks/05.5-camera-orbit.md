# Phase 5.5: Camera Orbit

## Status

`Completed`

## Objective

빈 공간 drag로 큐브 전체를 둘러볼 수 있게 합니다. DESIGN.md 7절이 확장 항목으로 남겨 둔 "empty drag → camera orbit"입니다.

Pointer down이 큐브를 빗나가면 orbit gesture가 시작되고, drag하는 동안 카메라가 큐브를 중심으로 한 구면 위를 움직입니다. Release하면 그 자리에서 끝납니다 — snap도, commit도, 애니메이션도 없습니다. 큐브를 잡은 gesture(Phase 5의 layer turn)는 그대로이고, 두 gesture는 pointer down 시점의 picking 결과로 갈립니다.

## Scope

- `graphics::OrbitCamera`: yaw/pitch로 파라미터화된 turntable 카메라와 pitch clamp
- Interaction state machine에 `Orbiting` 상태 추가 (down miss → 무시 대신 orbit 시작)
- Controller가 orbit 각도 변화를 내놓고 Application이 카메라를 갱신하는 연결
- Orbit 이후에도 picking이 옳게 동작함을 고정하는 native test
- 배경 drag가 큐브를 돌리고 논리 상태는 건드리지 않음을 확인하는 browser e2e

## Out of scope

- **Roll (시선축 회전)** — 아래 결정 참고. Orbit은 의도적으로 2 DOF입니다
- Zoom (카메라 거리 변경), pinch gesture
- 관성(놓은 뒤 계속 도는 것), orbit release 시의 정렬 snap
- 카메라 거리·fov 재조정 — 큐브 실루엣은 시점에 따라 최대 약 6% 커지지만(꼭짓점 정면 `√(8/3)` 대비 모서리 정면 `√3`), 현재 viewport 여유로 수용합니다. 손으로 재유도하는 대신 도달 가능한 전 범위를 훑어 확인하는 test를 두며, 측정된 최대 NDC 크기는 `0.854`로 여유가 충분합니다
- 전개도 영역에서의 특별 취급 — 큐브를 빗나간 press는 위치와 무관하게 전부 orbit입니다
- 키보드로 시점 변경, 시점 초기화 버튼 (Phase 6 UI에서 다룰 수 있음)

## Architecture decisions

### 카메라를 움직인다, model이 아니라

큐브 전체가 도는 그림은 model 회전으로도 카메라 이동으로도 만들 수 있고, roll까지 포함하면 둘은 같은 SO(3)입니다. 그러나 우리가 원하는 것은 3 DOF가 아닙니다.

- **Turntable orbit은 2 DOF가 전부이고, 그 편이 옳습니다.** 잃는 1 DOF는 roll인데, roll은 화면 속 큐브를 기울일 뿐이고 "위가 항상 위"를 깨뜨립니다. Drag 입력 자체가 (dx, dy) 2 DOF라서 3 DOF를 주려면 trackball처럼 궤적에서 roll을 누적시켜야 하고, 그러면 원을 그리며 drag할 때마다 큐브가 비스듬해집니다. yaw 무제한 + pitch clamp만으로 여섯 면이 전부 보이므로 roll 없이 부족한 것이 없습니다.
- **카메라 쪽이 기존 코드를 건드리지 않습니다.** Picking은 ray를 `inverse(projection × view)`와 `eye`로만 만들고 원점의 축 정렬 큐브와 교차시키므로, 카메라가 움직여도 변경이 없습니다. Drag resolver의 화면 방향 샘플링도 camera만 통합니다. Model을 돌렸다면 world와 cube-local이 갈라져 둘 다 역변환을 끼워 넣어야 했습니다 — Phase 5에서 12케이스 table로 부호를 고정한 바로 그 모듈들입니다.
- "Up과 시선이 평행이면 `look_at`이 깨진다"는 특이점은 pitch clamp 하나로 사라집니다. Quaternion 카메라도, 특별한 처리도 필요 없습니다.

### OrbitCamera: graphics가 소유하는 시점 상태

```cpp
namespace rubiks::graphics {

/** Turntable viewpoint: yaw about +Y, pitch above the horizon. Degrees. */
struct OrbitCamera {
    float yaw_degrees;
    float pitch_degrees;

    /** Adds a drag's angles, wrapping yaw and clamping pitch. */
    void turn(float yaw_delta, float pitch_delta) noexcept;

    [[nodiscard]] Camera to_camera(float aspect) const noexcept;
};

/** The viewpoint the rendered scene contract was derived from. */
[[nodiscard]] OrbitCamera home_orbit() noexcept;

inline constexpr float kPitchLimitDegrees = 80.0f;

}  // namespace rubiks::graphics
```

- Eye는 원점 중심, 반지름 `|(3, 3, 3)| = 3√3`인 구면 위에 있고 target은 원점, up은 +Y 고정입니다. Fov와 near/far는 `default_camera`의 값을 그대로 씁니다.
- `home_orbit()`은 기존 `default_camera`의 eye `(3, 3, 3)`에 해당하는 yaw 45°, pitch `asin(1/√3) ≈ 35.26°`입니다.
- **`default_camera`가 `home_orbit().to_camera(aspect)`로 위임하도록 바꿉니다.** 삼각함수로 재계산한 eye가 `(3, 3, 3)`과 bit 단위로 같다는 보장은 없으므로, 두 정의가 어긋날 여지 자체를 없앱니다 — Phase 5에서 `build_cube_scene`의 nullopt 경로가 기존 builder를 그대로 호출하게 한 것과 같은 무늬입니다.
- 다만 이것이 "기존 화면과 byte 단위로 동일"을 뜻하지는 않습니다. **측정하면 eye가 축마다 정확히 1 ulp(`2.4e-7`) 어긋납니다.** Application이 어차피 orbit에서 camera를 도출하므로 이 차이는 위임 여부와 무관하게 발생하고, 없애려면 home을 특수 취급해야 하는데 그럴 값어치가 없습니다. 실제로 보장되는 것은 **contract v3의 모든 검증점이 수정 없이 통과한다**는 것이고(sample이 sticker 중앙이라 1 ulp에 흔들리지 않습니다), 위임 덕분에 `home_orbit().to_camera(aspect) == default_camera(aspect)`는 float 완전 일치로 고정할 수 있습니다.

**회전은 quaternion으로도 행렬로도 표현하지 않습니다.** 상태는 두 각도이고, 카메라를 만드는 것은 회전 적용이 아니라 구면 좌표를 직교 좌표로 바꾸는 일입니다.

```cpp
const math::Vec3 eye{kDistance * std::cos(pitch) * std::sin(yaw),
                     kDistance * std::sin(pitch),
                     kDistance * std::cos(pitch) * std::cos(yaw)};
```

이후는 기존 `look_at(eye, origin, +Y)`가 처리합니다. Quaternion과 행렬은 회전을 **합성**해야 할 때 값어치를 하는데, turntable에서는 합성이 `yaw += Δyaw` 스칼라 덧셈입니다 — 2 DOF 선택이 회전 표현 자체를 없앤 것입니다(3 DOF trackball이었다면 Euler 각 덧셈이 성립하지 않아 quaternion 합성이 강제됩니다).

각도로 들고 있어야 하는 적극적인 이유도 있습니다. **Pitch clamp는 pitch가 명시적 변수일 때만 자연스럽습니다** — 행렬이나 quaternion에 담아두면 자를 때마다 Euler 각을 역추출해야 합니다. 증분 곱셈을 반복하면 float 오차가 쌓여 재정규직교화가 필요한 것도 각도 덧셈에는 없는 문제이고, 상태도 2 float로 끝납니다.
- Pitch는 `±kPitchLimitDegrees`로 clamp합니다. 위·아래 면을 보기에 충분하고 `look_at`의 특이점(±90°)에 닿지 않습니다. Yaw는 mod 360°로 감습니다.
- Aspect는 cube viewport가 정사각형이므로 지금처럼 1이지만, layout이 바뀌어도 따라가도록 인자로 받습니다. 이 인자가 `Camera::set_aspect`의 유일한 용도를 대체하므로 그 mutator는 제거합니다.

### Interaction: Orbiting 상태

```text
        down: cube hit                  up: axis lock 됨
 Idle ──────────────────▶ Dragging ──────────────────▶ Snapping
  ▲ ▲                        │                            │
  │ │  down: miss            │  (Phase 5와 동일)          │
  │ └───────▶ Orbiting       │                            │
  │               │          │                            │
  └───────────────┴──────────┴────────────────────────────┘
        up / cancel: orbit은 그 자리에서 종료
```

- **Down이 큐브를 빗나가면 이제 무시가 아니라 `Orbiting`입니다.** Viewport 밖(전개도 위 포함)의 press도 orbit입니다 — 큐브를 빗나간 drag의 의미는 위치와 무관하게 "둘러보기"입니다.
- Dead zone이 없습니다. Layer turn의 dead zone은 축 선택을 신뢰할 만큼 방향이 쌓이길 기다리는 장치인데, orbit은 선택할 축이 없고 commit도 없으므로 첫 move부터 반응하는 편이 좋습니다.
- 감도는 layer turn과 같은 각속도(“cube viewport 폭의 절반 drag = 90°”)를 기본값으로 하는 별도 상수입니다. 방향은 **큐브가 손가락을 따라 도는 쪽**입니다: 왼쪽으로 drag하면 보이는 면이 왼쪽으로 밀려나며 오른쪽 면이 앞으로 옵니다. 아래로 drag하면 윗면이 앞으로 옵니다. Layer drag에서 잡은 sticker가 손을 따라오는 것과 같은 감각이며, known-answer test로 고정합니다.
- **Orbit은 어떤 경로로도 `CubeState`에 닿지 않습니다.** Up과 cancel의 차이가 없습니다 — 되돌릴 commit이 없으므로 둘 다 “그 자리에서 종료”이고, 카메라는 움직인 곳에 남습니다. 시점은 취소해야 할 상태가 아니라 사용자가 이미 본 결과입니다.
- Resize는 Phase 5 정책 그대로 진행 중인 gesture를 (orbit 포함) 끝냅니다. 카메라 각도는 남습니다. Shutdown은 카메라를 `home_orbit()`으로 되돌립니다.
- `Snapping` 중의 press는 Phase 5대로 계속 무시합니다.

### `pointer_down`의 공개 계약이 바뀝니다

시그니처는 그대로지만 반환값의 의미가 "cube를 잡았는가"에서 **"gesture가 시작되었는가"**로 넓어집니다. Orbit도 gesture이므로 true를 반환하고, 덕분에 web의 "true일 때만 capture와 frame loop 시작" 규칙은 코드 변경 없이 orbit에도 적용됩니다. Phase 5.5 이후의 반환 규칙:

```text
1: Idle에서 유효한 좌표로 layer turn 또는 orbit gesture 시작
0: 초기화 전, non-finite 좌표, 이미 gesture 또는 Snapping 진행 중
```

조용히 지나가기 쉬운 의미 변경이므로, 옛 의미를 서술하는 모든 지점을 함께 갱신해야 합니다:

- `Application.hpp`의 "pointer grabbed the cube" 주석과 C ABI의 "1 = cube를 잡음" 주석
- `PointerTarget.pointerDown()`과 `onGestureStart`의 주석
- Native의 "빈 공간 down은 무시" test들 — 이제 orbit 시작을 단언하는 test로 바뀝니다
- TS unit의 "miss면 capture하지 않음" test — miss도 capture하는 계약으로 뒤집힙니다
- e2e "배경 press는 큐브를 건드리지 않는다" — `CubeState`에 대해서는 여전히 참이지만, 화면은 이제 도는 것이 정상입니다

### OrbitDelta: 증분 누적과 소비

Controller는 카메라를 소유하지 않습니다. `CubeMove`를 값으로 돌려주던 것과 같은 무늬로, orbit 중의 move는 각도 증분으로 바뀌어 나갑니다.

```cpp
namespace rubiks::interaction {

/** Orbit drag가 만든 시점 변화, 도 단위. */
struct OrbitDelta {
    float yaw_degrees;
    float pitch_degrees;
};

/** 마지막으로 꺼내 간 뒤 누적된 증분을 정확히 한 번 소비. 없으면 nullopt. */
[[nodiscard]] std::optional<OrbitDelta> take_orbit_delta() noexcept;

}  // namespace rubiks::interaction
```

- **누적 규칙**: move마다 **직전 pointer 좌표 대비** 증분을 계산해 pending 값에 더합니다. Pointer 이벤트는 rAF보다 잦을 수 있으므로, 여러 move의 증분이 덮어써지지 않고 합산되어야 합니다. `take_orbit_delta()`는 `std::exchange(..., nullopt)`로 정확히 한 번 소비합니다. Non-finite 좌표의 move는 Phase 5 규칙 그대로 무시합니다.
- **부호**: `yaw_delta = −dx × 감도`, `pitch_delta = +dy × 감도`. 위의 eye 공식과 합쳐 "왼쪽 drag → 오른쪽 면이 앞으로, 아래 drag → 윗면이 앞으로"가 됩니다.
- **Layer drag와 반대로 증분식입니다 — clamp 때문입니다.** Layer angle은 "down 지점부터 총 변위의 투영" 단일 공식이지만, orbit이 그 방식이면 pitch를 한계 너머로 한참 끈 뒤 되돌릴 때 총 변위가 한계 안으로 돌아올 때까지 화면이 반응하지 않습니다. 증분을 누적하고 **저장된 pitch를 clamp**하면, 한계에 붙은 상태에서 반대 방향 첫 move에 즉시 빠져나옵니다. 이 탈출 거동은 test로 고정합니다.
- Clamp와 yaw wrap(`[0°, 360°)`)은 각도가 사는 곳인 `OrbitCamera::turn`이 담당합니다. 증분 계산에 필요한 viewport 폭은 layer gesture처럼 down 시점에 capture합니다.
- `advance`는 `Orbiting`에서 true입니다 (drag 중에는 매 frame 그립니다). Up 이후에는 애니메이션이 없으므로 마지막 frame을 그리고 false로 돌아갑니다.

### Pending delta는 gesture보다 오래 삽니다

마지막 `pointer_move`와 다음 frame 사이에 up, cancel, resize, 새 down이 끼어들 수 있습니다. 여기서 delta가 유실되거나, 화면과 다른 camera로 picking하는 일이 없도록 계약을 고정합니다.

- **Up과 cancel은 pending delta를 보존합니다.** Orbit에는 되돌릴 것이 없으므로(위의 "up == cancel"), 사용자가 이미 만든 마지막 이동도 버릴 이유가 없습니다.
- **Application이 delta를 소비하는 지점은 셋뿐입니다**: 매 `advance`, `pointer_down`에서 controller에 camera를 넘기기 **직전**, 그리고 engine `resize()`가 gesture를 끝낼 때. 소비란 `take_orbit_delta → OrbitCamera::turn`입니다.
- 이 세 지점이 invariant를 만듭니다: **camera가 capture되는 순간, 그때까지 생산된 모든 orbit delta는 이미 적용되어 있습니다.** 그래서 render에 쓰는 camera, `pointer_down`에 넘기는 camera, drag resolver가 capture한 camera가 항상 같습니다.
- 별도의 정리 상태(`OrbitFinishing` 같은)를 두지 않습니다. 상태를 늘려 다음 down을 거절해도 "사용자가 이전 frame을 보고 조준한다"는 1 frame 경합은 사라지지 않고(Phase 5부터 있는 성질입니다), 16ms 사이의 press를 버리는 손해만 남습니다.
- Frame loop 쪽은 기존 보장으로 충분합니다: `advance`가 false를 반환한 frame도 그리므로, up 직후의 마지막 delta는 그 frame에서 소비되고 화면에 실립니다.
- Shutdown은 pending delta를 버리고 `home_orbit()`으로 돌아갑니다.

### Camera의 단일 출처

지금 Application은 mutable `Camera` 하나를 들고 resize 때 `set_aspect()`를 부릅니다. 여기에 `OrbitCamera`를 얹으면 진실이 둘이 됩니다. 그러지 않습니다:

- **Application의 시점 상태는 `OrbitCamera`(+ layout에서 오는 aspect)뿐이고, `Camera`는 필요할 때마다 `to_camera(aspect)`로 도출합니다.** 생성이 삼각함수 몇 개라 cache할 이유가 없고, cache가 없으면 "재생성을 잊는" 실수 자체가 불가능합니다.
- `Camera::set_aspect`는 호출자가 사라지므로 제거하고, `default_camera`의 fov·near/far·home eye 상수는 `OrbitCamera`와 공유하도록 헤더로 올립니다.

### Rendered scene contract와의 관계

Contract v3은 **home 시점의 계약**이 됩니다. 초기화 직후와 shutdown 후 재초기화 시점에는 지금과 완전히 같은 화면이므로 기존 검증이 수정 없이 통과합니다. Orbit 이후에는 3D sample과 seam 좌표가 당연히 무효지만, **전개도 54칸 검증은 카메라와 무관하므로 어떤 시점에서도 유효합니다** — orbit e2e가 "논리 상태가 변하지 않았다"를 단언하는 도구로 그대로 씁니다.

## Acceptance criteria

- 빈 공간 drag로 여섯 면을 모두 볼 수 있고, 위아래로는 pitch clamp에서 멈추되 반대 방향 drag에 즉시 반응합니다.
- Orbit은 `CubeState`를 절대 변경하지 않으며, up과 cancel의 결과가 같습니다.
- Pointer 이벤트와 frame의 상대 타이밍과 무관하게 delta는 유실도 중복 적용도 되지 않습니다.
- Render에 쓰는 camera, `pointer_down`에 넘기는 camera, gesture가 capture한 camera가 항상 같습니다.
- `default_camera`와 orbit의 home이 같은 camera를 내놓고, contract v3 test가 수정 없이 통과합니다.
- 도달 가능한 모든 시점에서 큐브가 viewport 안에 들어옵니다.
- Orbit 이후에도 큐브를 잡은 drag는 화면에 보이는 대로 layer를 돌립니다.
- Picking과 drag resolver는 같은 알고리즘을 유지하며, orbit된 camera에서 기존 test와 추가 test를 모두 통과합니다.
- 정지 상태에서는 frame loop가 돌지 않습니다 (orbit drag 중에만).
