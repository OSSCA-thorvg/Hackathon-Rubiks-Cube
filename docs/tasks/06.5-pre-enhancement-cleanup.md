# Phase 6.5: Pre-enhancement Cleanup

## Status

`Completed` — 1차(scramble 검사 제거, `is_busy` 개정)와 2차(외부 리뷰 반영: 상태 수명, renderer fail-stop, 접근성) 모두 완료.

## Objective

고도화(Phase 7~)에 들어가기 전에 기존 코드를 정리합니다. 1차는 이후 phase가 걷어내기로 결정한 두 곳의 선행 적용이고, 2차는 외부 리뷰가 짚은 상태 수명과 도달 불가 복구 구조의 정리입니다. 모든 항목은 후속 phase의 새 기능에 의존하지 않는 독립 삭제·개정이며, 공통 목표는 하나입니다 — **앞으로 상태가 누적될 자리를, 누적되기 전에 안전한 모양으로 바꿔 두는 것.**

1차에서 확인한 사실이 전제입니다: **두 동작 모두 고정하는 test가 어느 계층에도 없습니다.** Native test는 scramble 후 `!is_solved()`만 확인하는데 그 seed(42)는 검사 없이도 unsolved이고, orbit 중 busy를 단언하는 test는 native·TS unit·e2e 어디에도 없습니다.

## Scope

1차 (완료):

- `Application::scramble()`의 solved 검사와 R 덧붙임 제거 ([Phase 9](./09-move-queue-and-animated-scramble.md)의 결정을 선행 적용)
- `InteractionController::is_busy()`에서 `orbit_` 제외 (Phase 9의 결정을 선행 적용, [Phase 6](./06-gameplay-and-ui.md) 계약의 개정)

- 관련 주석 정리와 문서 기록

2차 (외부 리뷰 반영):

- Application의 전역 상태를 `ApplicationState` 하나로 묶고 수명을 `unique_ptr`로 관리
- Native test의 RAII fixture — assertion 실패에도 `shutdown()`이 보장되게
- Renderer resize의 rollback 제거 (fail-stop, [Phase 1](./01-wasm-vertical-slice.md) 계약의 개정)
- Timer `<output>`에 `aria-live="off"` 명시

## Out of scope

- Move queue, `Player`, tempo — 전부 Phase 9입니다. 이 phase는 기존 코드의 삭제·개정만 합니다
- `start_orbit()` 추가 — 소비자(재생 중 pointer 라우팅)가 Phase 9에서 생깁니다
- Scramble signature 변경(`move_count` 노출)과 seed 42 known-answer test 교체 — signature와 함께 움직이므로 Phase 9에 남습니다
- Phase 7의 snap 경계 변경 — 별도 phase의 본 작업입니다
- `AppLifecycle.teardown()`의 cleanup 예외 집계 제거 — 리뷰가 제안했지만 **유지합니다**. teardown이 불리는 시점이 정확히 engine 호출이 방금 던진 오류 경로라, 후속 cleanup(`pointer.teardown() → engine.pointerCancel()`)이 또 던지는 것은 인위적 가정이 아니라 정상 시나리오이고, 집계가 없으면 첫 throw에서 `engine.dispose()`가 영영 불리지 않습니다
- Controller 내부의 busy 술어 분리(`can_start_move()`류) — 리뷰가 제안했지만 두지 않습니다. 소비자가 하나뿐인 병렬 술어는 이전 리뷰에서 기각된 `is_turning()`의 반복이고, "mutation 차단"은 Phase 9의 app 수준 busy가 답합니다
- Pointer를 잡고 정지한 동안의 rAF 절약 — frame 소유권 계약을 복잡하게 만드는 데 비해 drag는 몇 초짜리이고, 탭 숨김은 Phase 10이 처리합니다
- 총 pixel area 상한, Vitest 정렬, `--emit-tsd` — 보류. 앞은 우선순위가 낮고 뒤 둘은 별도 확인이 필요합니다

## Architecture decisions

### Scramble의 solved 검사는 검증 불가능한 코드입니다

지금 `scramble()`은 수순을 적용한 뒤 결과가 solved면 R을 덧붙입니다. 이 경로는 도달할 수 없습니다 — `make_scramble`은 연속한 두 수가 같은 축을 쓰지 않으므로 짧은 수에서 identity는 축 제약만으로 구조적으로 불가능하고(상쇄에는 교환 가능한 두 수가 필요한데 그건 같은 축이라 막혀 있습니다), 20수에서는 확률이 10⁻¹⁹ 수준입니다. 도달하지 않는 분기는 test로 검증할 수 없고, 실제로 이 동작을 고정하는 test도 없습니다.

- 검사와 덧붙임을 지우고, "scramble은 생성된 수순을 그대로 적용한다"만 남깁니다.
- `Application.hpp`의 "deterministic **unsolved** scramble" 주석에서 unsolved 계약을 뺍니다. 우주적 우연으로 solved가 나오면 사용자가 Scramble을 한 번 더 누릅니다.
- Phase 9가 이 지점을 queue 재생으로 바꿀 때 이 결정 위에서 시작합니다.

### is_busy()의 orbit 포함은 계약이 아니라 구현의 우연입니다

Busy가 막는 대상은 cube를 바꾸는 입력인데 orbit은 commit이 없어(Phase 5.5의 "up == cancel") 막을 이유가 없습니다. Orbit이 포함된 것은 `InteractionController::is_busy()`가 내부 optional 네 개의 단순 조합이었던 결과이고, ABI 주석("gesture, snap, or commit")도 orbit을 말하지 않으며, 포함을 고정하는 test도 없습니다.

- `is_busy()`에서 `orbit_.has_value()`를 뺍니다. 관찰 가능한 변화는 "orbit drag 중에도 move 버튼과 keyboard turn이 살아 있다"뿐이고, 이는 개선입니다.
- Frame loop는 영향이 없습니다 — `advance()`의 반환값이 orbit을 `is_busy()`와 별개로 보고 있어, orbit 중 frame이 계속 도는 동작은 그대로입니다.
- 새 동작을 test로 고정합니다: orbit이 진행 중일 때 `start_move()`가 수락되고, `active_rotation()`은 snap을 보여 주고, orbit delta는 계속 누적됩니다.
- 이 개정의 결정과 근거는 Phase 9 문서에 있고, Phase 6 문서의 개정 기록이 계약 변경을 담습니다. 이 phase는 그 결정의 적용 시점만 앞당깁니다 — Phase 9의 queue 소비 loop가 이 술어를 그대로 쓰므로, 먼저 개정해 두면 그 phase는 새 동작 위에서 시작합니다.

### Application 상태는 목록이 아니라 객체 하나입니다 (2차)

지금 Application은 renderer, layout, orbit, cube, interaction, view mode, count가 익명 namespace 전역으로 흩어져 있고 `shutdown()`이 여덟 필드를 수동으로 초기화합니다. 계획대로면 여기에 Player, timeline, palette, ambient snapshot, restore buffer가 더해지므로, "reset 목록에서 하나 빠뜨림"이 가장 그럴듯한 미래 결함이 됩니다.

- 전역들을 `struct ApplicationState`로 묶고 `std::unique_ptr<ApplicationState>` 하나만 남깁니다. `initialize()`가 만들고 `shutdown()`이 파괴하며, `initialized` 플래그는 포인터 유무가 대체합니다.
- 소멸이 곧 전체 초기화이므로 shutdown의 수동 reset 목록이 사라지고, **필드 초기화 누락이 표현 불가능**해집니다 — timeline에 쓴 것과 같은 원리입니다.
- 공개 free-function ABI와 그 계약은 그대로입니다. 다중 인스턴스나 DI를 만들지 않습니다 — 상태의 수명을 타입에 맡기는 것뿐입니다.
- Native test에는 RAII fixture를 더해 REQUIRE 실패가 `shutdown()`을 건너뛰어 다음 test가 오염된 상태에서 시작하는 경로를 없앱니다.

### Renderer의 resize rollback은 소비자가 없습니다 (2차)

Target 교체 실패 시 이전 buffer로 재시도하고, 그것도 실패하면 unusable이 되는 rollback 분기가 있습니다. 그러나 유일한 실제 소비자인 web은 resize 실패를 반환값만 보고 **언제나 전체 teardown**으로 처리하므로, rollback의 성공과 실패는 밖에서 구분되지 않습니다. 그 분기는 production에서 도달할 수 없어 test 전용 virtual seam(`allocate_pixels`/`set_target` override)으로만 검증되고 있었습니다 — 도달 불가 경로를 test가 지키는 구조입니다.

- Target 교체 실패는 rollback 없이 renderer를 unusable로 만들고 false를 반환합니다 (fail-stop).
- 치수 검증과 allocation 선검사(실패 시 기존 target 보존)는 유지합니다 — 검증이 변경보다 앞이라 공짜입니다.
- Virtual seam 둘과 `ResizeFailureTest.cpp`, protected 생성자/`init()` 분리(test subclass용)를 함께 제거합니다.
- [Phase 1](./01-wasm-vertical-slice.md) 계약의 개정이므로 그 문서의 개정 기록에 남깁니다.

### 나머지 둘은 한 줄짜리입니다 (2차)

- Timer `<output>`은 암묵 `aria-live`가 polite라 매 frame 갱신이 스크린 리더를 계속 읽게 합니다. `aria-live="off"`를 명시합니다 — 최종 기록은 completion 안내(`role="status"`)가 이미 따로 읽습니다.
- `is_busy` 주석 네 곳(controller 헤더, Application 헤더, bindings, CubeEngine)에 orbit sweep이 busy가 아님을 명시합니다. 1차가 동작을 바꿨으므로 경계의 서술도 그 사실을 말해야 합니다.

## Acceptance criteria

- `scramble()`은 생성된 수순을 그대로 적용하며, solved 검사도 R 덧붙임도 재시도 경로도 존재하지 않습니다.
- 코드와 주석 어디에도 "scramble 결과는 unsolved"라는 계약이 남지 않습니다.
- `is_busy()`는 gesture, snap, 미소비 commit만 보고, orbit drag 중 `turn_face`와 move 버튼이 동작합니다.
- Orbit과 snap이 공존하는 새 동작이 native test로 고정됩니다.
- `advance()`의 반환값 의미(orbit 중 frame 지속)는 변하지 않습니다.
- Application의 상태는 `unique_ptr<ApplicationState>` 하나이고, `shutdown()`에 수동 초기화 목록이 없으며, 공개 ABI는 변하지 않습니다.
- Renderer의 resize는 fail-stop이고, virtual fault seam과 그 전용 test가 존재하지 않으며, 검증·allocation 실패 시 기존 target 보존은 유지됩니다.
- Timer는 `aria-live="off"`로 스크린 리더를 방해하지 않고, `is_busy`의 경계 주석들이 orbit 제외를 명시합니다.
- 새 test 외의 기존 test는 (제거되는 ResizeFailureTest를 빼면) 수정 없이 통과합니다.
- Native, WASM, TypeScript unit, browser e2e와 production build가 모두 통과합니다.
