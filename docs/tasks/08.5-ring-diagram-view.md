# Phase 8.5: Ring Diagram View

## Status

`Not started`

Phase 8 구현 직전 검토에서, 이 view의 배치를 "원의 교차점으로 유도"하려던 초안이 제약 충족 문제였음이 확인되어 **위치가 링을 정하는 쪽으로 뒤집었습니다**(아래 architecture decisions). 그 결과 이 phase는 Phase 8의 spline 생성기를 그대로 재사용하고, 실질 작업이 좌표와 `ViewMode` migration으로 줄었습니다.

Phase 8 v2 개정에서 분리되었습니다. 처음에는 "같은 링 기계에 배치 데이터만 다른 view"로 Phase 8에 얹으려 했으나, 외부 리뷰에서 두 가지가 그 요약보다 크다는 점이 확인되었습니다: 54개 스티커가 링 2개씩의 교차점이라는 topology 계약이 명시되어야 하고, `ViewMode` 값 하나 추가가 실제로는 Application render 분기 재구성을 포함한 전 계층 migration입니다. [Phase 8](./08-net-rotation-and-interaction.md)의 링 기계가 완성된 뒤 시작합니다.

## Objective

큐브를 (1,1,1) 대각선에서 본 투영을 편 **세 번째 화면**을 추가합니다.

세 축이 120° 간격의 세 중심이 되고, 아홉 링(3축 × 3층)이 전부 그 중심들 둘레의 **둥근 고리**가 되며, 54개 스티커가 고리들이 만나는 자리에 놓입니다. 전개도가 "면"을 보여 주는 화면이라면 이 view는 "링"을 보여 주는 화면입니다 — 회전이 곧 원 위의 순환이라는 큐브의 구조가 배치 자체에 드러납니다.

이 phase는 표시와 회전 동조까지입니다. 이 view에서의 조작(픽킹·drag)과 정교한 배치는 추후 UI 단계의 몫입니다.

## Scope

- 교차점 topology 계약과 그 test (아래 architecture decisions)
- 배치 데이터: 54개 슬롯 좌표, 그리고 아홉 링을 그 슬롯들을 지나는 loop로 그리기 (Phase 8의 spline 생성기 재사용)
- `build_rings_scene(state, rect, active)`: 정지 상태와 회전 동조 (Phase 8의 `cube/Surface` 순환과 링 기계의 위치 sampling 재사용)
- `ViewMode::Rings` 전 계층 migration: enum 값 3, C ABI 검증, `layout()`, Application render 분기 재구성, bindings 문서, TypeScript `CubeViewMode`, view 버튼
- Native test와 browser e2e

## Out of scope

- 이 view에서의 pointer 조작 — 배치가 확정되는 UI 단계에서
- 배치의 시각적 다듬기(간격, 색, 굵기) — UI 단계에서
- 안내선 — 이 view는 아홉 링이 항상 보이는 화면이므로 별도 안내선이 없습니다
- N ≠ 3 지원 — Phase 15

## Architecture decisions

### 교차점 topology가 이 view의 계약입니다

아홉 링에는 각각 12슬롯이 있어 membership이 108개지만 스티커는 54개입니다. 등식이 맞는 이유가 이 view의 구조입니다:

- **모든 스티커는 정확히 두 링에 속합니다.** 면의 normal 축 링에는 속하지 않고(그 축이 돌 때 이 스티커는 도는 면 위에서 제자리 회전하거나 무관합니다), 나머지 두 축에 대해서는 자기 좌표가 가리키는 layer의 밴드에 하나씩 속합니다. 54 × 2 = 108로 등식이 닫힙니다.
- 따라서 각 스티커의 슬롯 위치는 **서로 다른 두 axis family 링이 만나는 자리**이고, 아홉 링과 54개 슬롯이 이 view의 배치 전부입니다.
- 회전은 active ring을 따라 3슬롯 이동입니다. 이동한 스티커는 도착 교차점에서 **다른 축의 membership이 바뀝니다** — 원을 따라 돌다가 교차점에서 다른 원으로 갈아타는 그림이 되고, 이것이 이 view가 보여 주려는 것입니다.
- 도는 면의 9개 스티커는 그 면의 클러스터 중심 기준 제자리 회전입니다 (전개도와 같은 규칙).
- Topology 자체는 Phase 8의 `cube::ring_slots()`가 이미 답합니다 — 화면을 모르는 domain 함수라 이 view가 그대로 씁니다. 이 phase가 더하는 것은 슬롯의 **좌표**뿐이고, test는 "모든 스티커가 정확히 두 링에 속하고, 3슬롯 이동의 도착점이 domain의 순환과 일치"를 고정합니다.

### 이 view의 스티커는 축 정렬을 유지합니다

Phase 8은 셀을 "출발 슬롯 접선 대비 상대 회전"으로 기울입니다. 그것이 성립하는 근거는 전개도의 슬롯 접선이 전부 축 정렬이라 90° 도착 시 누적 회전이 90°의 배수라는 점인데, **이 view에서는 그 근거가 없습니다**: 슬롯이 다른 원과의 교차점이라 각도가 임의이고, 12슬롯이 원 위에 균등 간격이라는 보장도 없습니다(균등하다면 3슬롯 = 정확히 90°라 정사각형에는 안 보이겠지만, 교차점이면서 동시에 균등이라는 조건을 만족시킬 근거가 없습니다). 그래서 이 view는 링 기계에서 **위치 sampling만 재사용**하고 밴드 스티커는 이동 중에도 축 정렬을 유지합니다. 도는 면의 9개 클러스터만 전개도와 같은 규칙으로 제자리 회전합니다.

그래서 0°/90° 일치 test는 중심 좌표가 아니라 **quad의 네 꼭짓점까지** resting scene과 비교합니다. 중심만 보면 기울기가 남아 있어도 통과합니다.

### ViewMode 추가는 값 하나가 아니라 migration입니다

Application의 render는 지금 `view_mode != Net`(3D를 그릴까), `view_mode != Cube3D`(net을 그릴까) 같은 **부정 조건**으로 분기합니다. 값 3을 더하면 이 조건들이 조용히 참이 되어 Rings mode에서 cube와 net 경로가 잘못 실행됩니다. 부정 조건을 mode별 명시 분기(무엇을 그리는 mode인가)로 재구성하고, 같은 함정이 있는 곳(`pointer_down`의 라우팅, `valid_view_mode`, layout)을 함께 점검합니다.

경계를 지나는 나머지는 기계적입니다: C ABI 값 3과 검증, `layout()`의 rings rect, TypeScript `CubeViewMode`와 `VIEW_NAME_BY_MODE`, bootstrap의 버튼 하나.

**이 view의 `pointer_down()`은 부작용 없이 `false`를 반환합니다.** 조작이 범위 밖이므로 gesture를 시작하지 않고, Phase 7이 세운 "거절 사유는 전부 snap 확정보다 먼저"에 따라 진행 중인 snap을 확정하지도 않습니다. Net mode가 전개도 밖 press에 대해 하는 것과 같은 규칙입니다.

### 원이 위치를 정하는 게 아니라 위치가 원을 정합니다

초안은 반대였습니다: 세 중심과 아홉 반지름만 저장하고 54개 좌표를 원의 교차점으로 **유도**하라고 했습니다. 이중 source of truth를 피한다는 좋은 의도였지만 결과가 뒤집힙니다 — 그러면 "아홉 원이 각각 다른 여섯 원과 정확히 2점씩 만나고, 54개가 서로 다르고, triple intersection이 없고, 각 원 위의 cyclic order가 `cube::ring_slots()`와 일치"를 동시에 만족하는 중심·반지름을 찾아야 하고, 이것은 배치가 아니라 **제약 충족 문제**입니다. 초안이 "과제약이면 후퇴한다"는 조항을 달고 있었던 것이 그 신호였고, "자세한 배치는 UI 단계에서"라는 방침과도 반대 방향입니다.

그래서 뒤집습니다. **54개 슬롯 좌표를 먼저 정하고, 아홉 링은 각자의 12슬롯을 지나는 닫힌 loop로 그립니다 — [Phase 8](./08-net-rotation-and-interaction.md)의 그 cardinal spline 생성기 그대로입니다.**

- 제약 충족 문제, triple intersection test, 후퇴 조항이 전부 사라집니다.
- "각 스티커가 두 링 위에 있다", "각 링 위의 cyclic order가 `cube::ring_slots()`와 일치한다"가 검증할 제약이 아니라 **구성상 참**이 됩니다.
- 재사용이 완전해집니다: 같은 loop 생성기, 같은 `RenderStroke`, 같은 위치 sampling. 이 phase의 실질 작업이 "좌표 + `ViewMode` migration"으로 줄어듭니다.
- 그림은 참조 이미지대로 읽힙니다 — 겹치는 아홉 개의 둥근 고리. 정확한 원이어야 할 이유가 없습니다.
- 배치를 UI 단계에서 자유롭게 손봐도 test가 깨지지 않습니다. test가 좌표가 아니라 구조를 고정하기 때문입니다.

좌표의 초기값은 여전히 세 중심(120° 간격)과 아홉 반지름에서 뽑습니다 — 개수가 맞아떨어지는 것이 이 배치가 말이 되는 이유이기 때문입니다: 중심쌍 세 개 × (3 × 3 원 쌍) = 27쌍, 각 쌍의 교차점 2개 = **54**. 한 원은 다른 두 중심의 원 3 + 3개와 만나 6 + 6 = **12슬롯**. 다만 그것은 **초기값을 만드는 규칙**이지 지켜야 할 계약이 아닙니다. 한 쌍의 두 교차점 중 어느 쪽이 어느 sticker인가는 눈으로 맞추면 되고, 어긋나도 그림은 여전히 옳습니다.

## Implementation steps

### 1. Topology와 배치

- [ ] 스티커 → (링, 슬롯) × 2 mapping과 test: 모든 스티커가 정확히 두 링, 합계 108 membership
- [ ] 54개 슬롯 좌표 (초기값은 세 중심 120° + 아홉 반지름의 교차점에서 뽑되, 계약이 아니라 규칙)
- [ ] 좌표 test: 54개가 서로 다름, 링당 12개
- [ ] 3슬롯 이동의 도착점이 domain 순환과 일치하는 test

### 2. Scene builder

- [ ] `build_rings_scene(state, rect)`: 아홉 링의 stroke(Phase 8의 spline 생성기에 이 view의 12슬롯을 넣어) + 54 슬롯의 스티커 quad
- [ ] `build_rings_scene(state, rect, active)`: active ring 위의 슬롯 이동(위치 sampling만, 스티커는 축 정렬 유지) + 도는 면 클러스터 제자리 회전
- [ ] Scene test: 정지 상태 54슬롯 색, 0°/90° 일치(quad 네 꼭짓점까지 비교), 회전 중 슬롯이 링 곡선 위에 있음

### 3. ViewMode migration

- [ ] Application render/pointer_down의 부정 조건 분기를 mode별 명시 분기로 재구성
- [ ] `ViewMode::Rings` 추가: enum, `valid_view_mode`, C ABI 값 3, bindings 문서
- [ ] Rings mode의 `pointer_down()`이 부작용 없이 false: 진행 중 snap이 확정되지 않는 test
- [ ] `layout()`의 rings rect
- [ ] TypeScript `CubeViewMode`, `VIEW_NAME_BY_MODE`, bootstrap 버튼
- [ ] 기존 세 mode의 동작이 변하지 않는 test (분기 재구성의 회귀 방지)

### 4. Verification

- [ ] Rings mode 렌더링의 native raster test (sample point)
- [ ] e2e: 버튼 전환, 그리고 회전 동조 — **drag 중 전환은 gesture를 취소하므로**(Phase 6의 계약) release로 snap을 시작한 뒤 snap 도중 Rings로 전환해 중간 frame을 확인하거나, Rings mode에서 programmatic turn으로 확인합니다
- [ ] Native, WASM, TypeScript unit, e2e와 production build 전체 실행

## Acceptance criteria

- 54개 스티커가 각각 서로 다른 두 axis family 링에 속하고, membership 합계가 108로 닫힙니다.
- 어느 축의 회전이든 active ring 위의 스티커가 그 링의 곡선을 따라 이동하고, 0°와 90°에서 논리 상태와 정확히 일치합니다.
- Rings 버튼으로 전환되고, 회전이 3D·전개도와 같은 frame에 동조합니다.
- 기존 세 view mode의 렌더링과 pointer 동작은 변하지 않습니다.
- Rings mode의 press는 아무 gesture도 시작하지 않고 진행 중인 snap도 확정하지 않습니다.
- 밴드 스티커는 이동 중에도 축 정렬을 유지하고, 0°와 90°에서 quad의 네 꼭짓점이 resting scene과 일치합니다.
- `RenderScene`은 ThorVG type을 포함하지 않고, ThorVG 호출은 renderer 안에만 있습니다.
- Native, WASM, TypeScript unit, browser e2e와 production build가 모두 통과합니다.
